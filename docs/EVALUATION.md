# Evaluation

How we measure the Fraud Detection System, what the results are, and what they don't show.

## Method

- **Dataset:** `data/transactions.csv`, with 120 synthetic transactions across 12
  customers, generated by `scripts/generate_data.py` with a fixed seed so anyone
  can reproduce it. Each row is labelled `clean`, `fraud` or `borderline`, plus
  `is_fraud`. About 30% of the borderline cases are real fraud.
- **What runs:** `python -m src.evaluate` uses the same scoring functions as the
  live agents (`evaluate_rules`, `evaluate_behaviour`, `adjudicate`). The LLM is
  skipped because it only writes explanations and can't change a decision, so
  all 120 cases take about a second.
- **How review counts:** a fraud sent to human review counts as *detected*,
  because a person sees it. Review volume is reported separately, since it costs
  analyst time.

## Results

These are the current numbers. The full, regenerated report is
[results/evaluation_report.md](../results/evaluation_report.md), and the
per-transaction results are in `results/evaluation.csv`.

| Metric | Value |
|---|---|
| Fraud detected (declined or reviewed) | **87%** (20 of 23) |
| Fraud auto-declined | 78% |
| Fraud missed (approved) | 13% (3) |
| Genuine customers wrongly declined | **0%** (0 of 97) |
| Traffic sent to a human | 9% (11 cases) |

All 18 obvious frauds are declined automatically and all 81 clean transactions
are approved automatically. Borderline cases split between approve and review.

## The three misses

| Transaction | Amount | Only signal |
|---|---|---|
| T1022 | £117.71 | unusual category |
| T1101 | £55.42 | unusual category |
| T1113 | £173.05 | unusual category |

These are low-value frauds that look normal apart from one weak signal. Lowering
the approve threshold far enough to catch them also sends many genuine
customers to review. Better fixes are new signals rather than lower thresholds: device history (a
new device for this customer) or a network check (does this payee link to
flagged accounts?).

## Regression gate

`tests/test_evaluation.py` runs in CI and fails if:

- detection drops below 85%
- any genuine customer is auto-declined
- more than 15% of traffic goes to review
- any obvious fraud is approved, or any clean transaction is not

## What this does *not* show

- **Real-world accuracy.** The data is synthetic, and we generated the
  scenarios the rules were designed for, so real fraud is more varied. Treat
  these numbers as a check that the system behaves as designed, not as a fraud
  detection benchmark.
- **The quality of the LLM explanations.** Those are checked by hand. They can
  misstate numbers (for example "200% above typical" when it's about 12×),
  which is why the dashboard shows the computed flags beside them.
- **Latency at scale.** On a laptop CPU each LLM explanation takes about 5–12
  seconds (see the `trace` timings in `results/sample_audit_log.jsonl`). The
  rules themselves take under 1 ms.
